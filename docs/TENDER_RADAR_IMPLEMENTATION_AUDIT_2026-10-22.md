# Tender Radar 实现一致性审查

审查日期：2026-10-22  
需求基线：[双栏目 PRD V0.1](TENDER_RADAR_DUAL_CHANNEL_PRD_V0.1.md)  
审查方式：当前分支静态代码审查；没有访问生产数据库、服务商账单或真实浏览器运行状态。

## 结论

当前实现已经具备招标阶段筛选、业务规则版本管理、人工复核、请求次数熔断和可配置采集时段等基础。仍有三类整体性问题：

1. 之前的行业动态页面用固定样例冒充真实资料，收藏和取消关注只保存在浏览器内；PRD 已将行业动态列为 P1，这些页面行为会造成能力已上线的错觉。本轮已将其改为明确的待上线页并从正式导航隐藏。
2. 首页过去写死最近更新时间，后台也允许 4 个时段；公众号采集没有遵守统一时段。本轮改为读取实际计划与信源成功记录，时段上限收敛为 3，并使公众号任务遵守同一采集窗口。
3. 仍存在需要产品确认或下一轮重构的规则硬编码，尤其是马鞍山软件运维特例和 2026 节假日日历；费用展示也未覆盖全部付费采集服务。

本审查只将“代码存在”记为已实现，不把真实采集、模型不可用恢复、费用结算或浏览器流程标成已验收。

## 模块化与效率审查

- `packages/backend/src/sources/collect.ts` 原先混合来源调度、采集、X 分片和自动调频。本轮已将到期调度、手动批次、间隔自适应移入 `sources/scheduler.ts`，并把共享采集日历读取集中到 `sources/schedule-config.ts`；`collect.ts` 仍负责单来源和 X 分片采集，后续可继续按 I/O 边界拆分。
- `packages/backend/src/editorial/analyze.ts` 约 766 行，承担多阶段分析、模型回退、结果归并和失败状态。建议先按阶段拆小纯函数与 I/O 边界，不改变调用顺序、回执或重试语义。
- 精选规则原先同时写在 `industry/prompts/prefilter.md` 和 `editorial/writing.ts` 的运行时 rubric 中，截止语义已出现分叉。本轮移除重复 rubric，并将动态精选门槛放回有内容哈希版本的 prompt 文件。
- `packages/backend/src/publication/publish.ts` 同时计算公开状态并处理特例选中规则。建议将可测试的选择规则与数据库投影写入分层；地域特例数据化后再移除硬编码分支。
- `adaptIntervals()` 原先对每个来源逐条执行 `UPDATE`。本轮已改为先在内存计算，再通过一次 `UPDATE ... FROM unnest(...)` 批量写回；各类来源原有间隔策略不变，数据库往返由每个变更来源一次降为每轮最多一次。
- `collectSource()` 的资料入库和任务排队当前串行。它们依赖唯一键、版本修订和副作用顺序；不应仅为提高吞吐而直接并发化。先用运行指标确认瓶颈，再按有界并发与幂等边界优化。
- 当前只发现 `actual-cost.ts` 和 `regional-selection.ts` 各有一个对象形状保护函数。暂不增加公共工具层，避免为了两处轻量重复建立过度抽象。

## 本轮修改

- 招标侧栏名称改为“招标信息”；行业动态从正式导航移除。
- `/industry` 改为待上线说明，不再显示虚构文章、分数、发布日期、正文、收藏和关注状态。
- 首页采集时段和最近成功时间改为 API 提供的运行数据；公开摘要在 API 侧短缓存，并使用 `publication/` 读取层。
- 公众号轮询改为共享全局采集时段；worker 每分钟只检查/入队，真正付费请求仍由来源任务执行。
- 全局采集时段上限由 4 调整为 3。
- 根据用户确认，将招标 70/20/10 默认评分、地域范围与马鞍山软件运维特例写入 PRD；从 P1 中移除地域偏好。
- 分析提示中的截止规则统一为“临近截止只扣减时效分，是否精选按 PASS 与综合分门槛判断”。
- 删除重复拼接的运行时评分 rubric，将精选门槛纳入 prompt 文件及其内容哈希版本。
- 自动调频从逐来源更新改为单次批量更新，减少数据库往返。
- 将常规来源调度/手动批次/自动调频从采集执行模块拆至 `scheduler.ts`，并统一采集日历读取。
- PRD 首页状态、原始评审边界和本次实现审查链接已更新。
