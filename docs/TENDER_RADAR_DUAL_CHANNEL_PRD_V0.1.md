# Tender Radar「招标信息 + 行业动态」产品需求文档

版本：V0.1 交流评审稿
日期：2026-10-13
面向读者：公司负责人、业务人员、产品与研发人员
本次交付：需求与页面结构设计。本文新增能力均为拟议需求，不代表已经上线；本次不编码、不充值、不启用新信源。

## 1. 产品定位与已确认事项

让同一套信源同时服务公司的两件事：**找可以跟进的项目，了解值得学习的技术与同行动向。**

它和持续追踪热点的新闻产品定位不同：本产品优先保证内容长期积累、可检索、可回看和可反馈，不追求每几分钟刷新一次热点榜。对招投标和行业研究来说，一天两次已经能满足大多数阅读和跟进需要；“新”是筛选条件之一，不是唯一价值。

| 栏目 | 用户要回答的问题 | 内容范围 |
| --- | --- | --- |
| 招标信息 | 有什么项目？处于哪个阶段？与我们有什么关系？还来得及参与吗？ | 招标采购、标前信息、中标信息 |
| 行业动态 | 同行在做什么？有什么软件和方法值得了解？哪些研究可能用于我们的业务？ | 公众号文章、企业新闻、产品更新、技术实践、案例、论文、相关政策标准 |

已确认的要求：

- 原首页“项目信息”分组改称“招标信息”；保留招标采购、标前信息、中标信息三个入口及其行业分类。
- 新增行业动态，技术、软件与研究方法，以及同行企业、产品与项目动向，**同等重要**。
- 重点关注地质与矿业、水利水务、政务相关业务；行业与技术的具体分类在本文提出供讨论。
- 首批关注对象包括公众号“地质”，以及新点软件、超图软件、龙软、3DMine、迪迈。
- 采用之前认可的浅蓝配色、左侧一级菜单、中间行业二级菜单和右侧内容区；保留时间轴与有依据的 AI 评分。
- 自动拉取默认每天两次，按北京时间 08:00、17:00 执行，后台可以调整为每天 2–3 次；行业动态不采用持续追热点式抓取。
- 用户当前 DeepSeek 尚未充值。产品需具备 AI 不可用时仍能阅读、收录与整理的基本能力。
- 地域属于 P1，留待后续讨论；已知关注江苏、安徽、江西、河北。此次不将这些地域作为行业文章的排除条件。

本稿不扩展为客户管理、投标文件编写、自动联系企业、自动采购软件或论文服务。

## 2. 现有基础与关键缺口

以下根据 2026-10-13 的本地仓库检查，区分“已有基础”和“本期要求”；没有查询或确认任何服务商账户余额。

| 已有基础 | 本期需要补足 |
| --- | --- |
| 已有官网、订阅源、接口、公众号、外部导入等采集方式 | 同一信源可供应不同栏目，按每篇内容判断去向 |
| 已有企业业务匹配、内容评分、摘要、主题和日报机制 | 招标匹配与行业参考价值分开判断，避免研究文章因没有采购任务而被过滤 |
| 已有微信公众号采集接入，依赖第三方付费服务配置 | 首批账号核验、可读性验证、费用展示、读取失败后的补充路径 |
| 已有按分钟、小时、天限制付费请求次数的功能 | 统一的两次采集计划、分项费用展示、可理解的预算设置 |
| 首页显示“每日 08:00、17:00 更新” | 当前该提示及“最近更新”是固定文案，后台仍按信源间隔调度；需让实际运行与页面一致 |
| 已有 AI 处理与结果展示 | 明确 AI 暂停时的收录、展示、补分析规则，不让栏目变成空白 |
| 已有文章摘要与原文链接 | 本地 Markdown 快照、站内完整阅读、收录时间与原文发布时间分开显示 |

特别说明：后台定时检查是否有任务，与真实向外部信源发起请求不是一回事。后续验收要看实际采集记录和付费请求记录，不能只看页面上的时间提示。

## 3. 页面与导航设计

### 3.1 左侧一级菜单

保留现有三个招标入口的地位，只增加一个行业动态入口，避免为了新增栏目再次把导航层级弄乱。

| 左侧分组标题 | 一级菜单 | 用途 |
| --- | --- | --- |
| 招标信息 | 招标采购 | 当前可关注的采购项目 |
| 招标信息 | 标前信息 | 采购意向、需求调查、前期公示等 |
| 招标信息 | 中标信息 | 中标、成交及相关结果信息 |
| 行业观察 | 行业动态 | 技术研究、同行动向及相关资料的统一入口 |
| 常用 | 商机日报、收藏 | 保留已有入口；收藏可按招标与行业内容区分 |
| 管理 | 后台管理 | 信源、规则、采集计划、费用与系统设置 |

首页默认仍进入招标采购。行业动态是并列栏目，不与招标公告混成一条列表。行业动态周报可在 P1 增加，无需首期增加更多一级菜单。

### 3.2 中间二级菜单：按行业看

点击行业动态后，中间一列显示行业导航，沿用用户认可的设计。建议候选分类：

| 行业 | 首批重点主题 |
| --- | --- |
| 全部行业 | 跨行业查看 |
| 地质与矿业 | 三维地质建模、隐式建模、地质软件、矿业信息化 |
| 水利水务 | 数字孪生水利、水文与监测、水利信息化、业务模型 |
| 数字政府与城市治理 | 政务服务、数据治理、公共资源交易、业务平台 |
| GIS 与测绘地理信息 | 空间数据、三维 GIS、遥感、测绘、空间分析 |
| 数字建筑与智慧工地 | 与公司关注方向相关的软件、数据和监管场景 |
| 其他相关业务 | 暂时无法放入前述分类但已确认相关的内容 |

“地质与矿业”需要明确出现，不能把地质建模研究全部埋在泛化的“数字矿山”里。AI、数字孪生、隐式建模等跨行业技术作为专题标签，不因涉及 AI 就另造一个行业。

这些分类是评审建议。关注某个研究方向并不意味着公司已具备该方向的承接能力，不自动改写原来的招标能力档案。

### 3.3 右侧工作区：按内容类型与对象筛选

顶部标题示例：**行业动态 · 地质与矿业**。

- 搜索框：搜索文章、企业、软件、技术主题、作者。
- 一排内容类型：全部、产品与软件、企业动向、项目案例、技术研究、学术论文、政策与标准。
- 筛选项：关注企业、技术主题、来源、发布日期；复杂筛选放在“更多筛选”中。
- 列表视图：今日获取、最近 7 日、历史资料、全部、推荐、仅看收藏。默认进入“今日获取”；“最新”按收录时间排列，不再把原文发布日期和抓取时间混为一个排序字段。
- 技术研究与同行动态不预设谁更重要，也不按网络热度分配展示资格。

几个维度要分清：**公众号是来源渠道；隐式建模是技术主题；地质是行业；论文是内容类型；超图是关注企业。** 用户可以组合这些条件，不必在同一层级反复切换。

### 3.4 列表与详情

保留日期分组和时间轴。招标行继续显示预算、发布日期、截止日期与剩余时间；行业动态使用自己的内容布局。

行业动态每条显示：

1. 标题，最多两行，不把关键内容挤成看不懂的缩略。
2. 来源、作者或机构、原文发布日期、内容类型。
3. 两三行摘要，说明介绍了什么；有 AI 分析时，再显示“为什么与你有关”。
4. 企业、产品或技术主题标签。
5. 已分析时显示“AI 参考价值”；未分析时显示“待分析”，不能显示为 0 分。
6. 收藏、站内阅读、不感兴趣。原文链接作为来源追溯入口放在详情页底部，不作为打开文章的主要动作。来源和标签只显示一遍，不在右侧再复制一组。

只有日期的文章不编造小时；未知发布日期显示“日期待核实”，另列收录日期，不混入“今日发布”。

详情页按内容提供补充信息：

| 内容 | 详情重点 |
| --- | --- |
| 软件产品 | 解决什么问题、适用业务、版本与功能变化、试用或文档原文入口 |
| 企业动向 | 哪家企业、做了什么、涉及哪些产品或客户、对关注方向的关联 |
| 项目案例 | 应用场景、客户与交付范围、已知项目阶段；明确不是待投标项目 |
| 技术研究 | 问题、方法、适用场景、实施条件、局限与作者观点 |
| 学术论文 | 原题与中文题意、作者机构、发表信息、研究问题、方法、局限、论文和代码链接 |
| 政策标准 | 发布机构、适用范围、发布时间、生效时间、可能影响的业务 |

资料缺什么就显示缺什么。只读到论文摘要时，明确标为“基于摘要”，不生成声称读过全文的结论。厂商宣称的效果与独立验证结果分开标注。

### 3.5 站内 Markdown 阅读器与资料时间线

抓取完成后，每篇文档形成一份可追溯的本地 Markdown 快照，并在系统内直接阅读。阅读路径不跳转到公众号或网页；原文链接保留在详情底部，用于来源核验、原文未能获取时的补充入口。

本地资料快照至少保存：

- Markdown 正文：标题、作者、发布时间、摘要、一级和二级标题、段落、列表、引用、表格、代码块、图片说明和原文链接。
- 附件与图片：使用本地可持久化的资料目录保存，正文引用相对路径；加载失败时显示图片或附件名称及缺失状态。
- 来源信息：来源名称、原文地址、首次发现时间、最近抓取时间、正文版本和内容指纹。
- 处理状态：正文完整、仅摘要、正文部分缺失、等待人工补录、已保存 Markdown。

“保持原样”按内容结构和阅读层级实现，不承诺复制公众号的所有 CSS 和互动组件。微信卡片、投票、音视频、外部小程序等无法用 Markdown 表达的部分，显示为兼容占位、截图或附件说明，并标明没有被转换的内容。系统不因无法完整还原页面样式而伪造正文。

阅读器页面建议采用左侧文章目录、中间正文、右侧资料信息：

| 区域 | 内容 |
| --- | --- |
| 左侧 | 标题层级目录、返回列表、上一篇／下一篇 |
| 中间 | 本地 Markdown 渲染的正文，图片、表格、引用和代码块可读 |
| 右侧 | 来源、作者、原文发布、系统收录、状态、行业、主题、AI 参考价值、收藏；来源旁显示“已关注”和“取消关注／停用信源” |
| 底部 | “已保存 Markdown”、版本记录、原文追溯链接；下载 Markdown 放入“更多”菜单，不作为主按钮 |

系统在抓取完成后自动保存 Markdown 和本地附件，用户不需要主动下载才能在系统内阅读。下载是资料迁移或备份时的次要操作，入口统一放在“更多”菜单，避免把阅读页面做成文件下载页。

### 3.6 当前抓取与历史文章的视觉区分

文档使用两个时间字段，避免混淆：**原文发布于**和**系统收录于**。一篇 2024 年的论文今天第一次抓到时，可以同时显示“历史资料”和“今日获取”；它不应伪装成今日发表，但应出现在今日获取计数里。

列表和二级菜单使用以下标识：

| 标识 | 判定依据 | 用途 |
| --- | --- | --- |
| 今日获取 | `系统收录于` 为今天，且是新建文档，不是重复抓取或内容刷新 | 表示本批次真正获得的资料 |
| 最近 7 日 | 系统收录时间在最近 7 天 | 查看近期积累 |
| 历史资料 | `原文发布于` 超出当前关注时间窗，或来源明确为历史回溯 | 区分知识库资料与近期动态 |
| 内容更新 | 已有文档正文发生新版本变化 | 表示原文有后续变化，不增加重复文档 |

“今日获取”和“历史资料”允许同时出现。默认列表按系统收录时间分组；进入“历史资料”后按原文发布时间和主题检索。每行同时显示“原文发布：2026-10-09”“系统收录：2026-10-13 17:00”。

中间二级菜单上的数字只表示**今天实际新获取的文档数**，不表示未读数、历史总数、原文发布数或 AI 分析数。例如“地质与矿业 12”悬停或点击后显示“今日获取 12 篇”；没有新增时显示 0 或不显示，规则全站一致。顶部再显示“今日获取 12 · 历史资料 2,481”，让当前批次和知识库总量同时可见。

### 3.7 轻量色彩层级

工作区保持浅蓝底和蓝色主操作，增加低饱和的状态色来区分资料阶段与内容类型，不使用高饱和色块或渐变：

| 色彩层级 | 使用场景 | 传达的信息 |
| --- | --- | --- |
| 浅蓝 | 当前选中、今日获取、主按钮 | 当前正在处理的内容 |
| 暖象牙色 | 历史资料、老论文、历史回溯 | 内容较早，但仍可检索和参考 |
| 淡紫 | 技术研究、论文、方法资料 | 需要阅读和研究的知识内容 |
| 淡薄荷绿 | 已保存 Markdown、正文完整、已收藏 | 资料已在系统内保存，可直接阅读 |
| 淡琥珀色 | 待分析、正文部分缺失、待核实 | 需要后续处理或人工确认 |

颜色只作为标签、左侧边线、轻微行底色和状态徽标使用；文字仍以深蓝灰为主，保证表格和正文的可读性。相同含义在首页、阅读器和后台统一使用同一色彩，不让颜色替代文字。

## 4. 内容范围与分流规则

### 4.1 内容类型

| 类型 | 应收录的内容 | 需要降权或排除的内容 |
| --- | --- | --- |
| 产品与软件 | 新产品、版本更新、功能讲解、技术文档、有信息量的软件比较 | 只喊“领先”“赋能”，没有具体功能或变化的广告 |
| 企业动向 | 同行业务布局、产品合作、业务相关的重大进展 | 节日祝福、普通团建、与业务无关的宣传 |
| 项目案例 | 有明确场景、客户、方案和交付内容的案例 | 缺乏实质内容的获奖或活动通稿 |
| 技术研究 | 个人或团队的方法介绍、教程、经验、实测和业务研究 | 拼凑文章、与业务无关的泛科普 |
| 学术论文 | 与关注主题相关的期刊、会议、预印本论文 | 仅靠关键词擦边、无法确认论文来源的宣传 |
| 政策与标准 | 与地质、水利、政务、数据、GIS 等业务直接相关的政策与标准 | 缺少业务关联的一般政务新闻 |

个人文章可以有很高的参考价值；官方文章也可能信息量低。来源身份用于提示可信程度，不替代对文章本身的判断。

### 4.2 归入哪个栏目

| 实际内容 | 应如何处理 |
| --- | --- |
| 公众号介绍三维隐式地质建模方法 | 行业动态 → 技术研究；不要求存在采购任务 |
| 软件厂商发布新版本 | 行业动态 → 产品与软件；不是招标采购 |
| 新点发布某政务平台交付案例 | 行业动态 → 项目案例；已交付不能标成待投标 |
| 政府正式发布软件采购公告 | 招标信息 → 招标采购 |
| 政府正式发布采购意向 | 招标信息 → 标前信息 |
| 交易平台发布中标结果 | 招标信息 → 中标信息；涉及关注企业时可在其相关资料中引用 |
| 企业自称中标，未取得正式结果公告 | 行业动态 → 企业动向，注明为企业披露；不冒充正式中标公告 |
| 一篇公众号文章同时含技术解读和采购公告链接 | 技术解读保留在行业动态；公告作为独立原始资料进入招标栏目，并相互关联 |
| 只看得到标题，无法辨别性质 | 标为待分类，由管理员补充或确认，不能凭猜测进入招标栏目 |

同一份原始资料只采集和保存一次，可以关联多个行业、企业和专题。多个视图引用同一记录；不因为有两个栏目，就对同一公众号重复付费查两次。

### 4.3 招标与行业动态共用关键词，但不共用结论

两类内容可以共用一套实体和主题词表，例如“地质”“水利”“GIS”“三维建模”“数字孪生”、地区、企业名、产品名和项目名。这样公众号文章与招标公告能互相找到，也能减少重复维护关键词。

但最终判断要使用两套规则：

| 共用线索 | 招标信息还要确认 | 行业动态还要确认 |
| --- | --- | --- |
| 行业、地区、企业、产品、技术主题 | 是否存在本次采购、标包、交付物、预算、截止时间和项目阶段 | 是否有新知识、产品变化、技术方法、案例或长期参考价值 |
| “平台”“系统”“测绘”“建模”等词 | 词是否落在真实采购任务里，而不是背景或附带义务 | 内容是否具体，是否有方法、版本、证据或可核验原文 |
| 企业名称 | 企业是采购方、供应商、代理还是被引用对象 | 企业是发布者、被报道者、合作方还是案例主体 |

因此，“关键词共用”可以做成共享词典和搜索入口；“是否入选、如何展示、怎样评分”不能只靠一套关键词规则直接复用。

### 4.4 去重、后续进展与历史资料

- 同一文章被官网、公众号和媒体转载，列表优先展示一条，并能展开其他来源；优先引用可确认的原始发布者。
- 内容真正有变化，如新版本、新实验、新进展，应单独呈现为后续内容，不能只因标题相似而吞掉。
- 企业名使用别名归一；企业、品牌、软件产品分别记录，不将名称相似的不同对象自动合并。
- 论文优先按论文标识及正式出版信息核对；预印本与正式版关联展示，不简单当成两项研究突破。
- 首次添加信源后，历史文章按原文日期归档，不伪装为今日新闻。
- 有价值的老论文、经典方法仍可被收藏、搜索和专题引用；“旧”不等于研究价值低。新转载须保留原始研究日期。

## 5. 两套价值判断与 AI 评分

| 项目 | 招标信息 | 行业动态 |
| --- | --- | --- |
| 核心问题 | 是否有真实采购任务，是否与公司能力相关 | 是否有相关知识、产品进展或同行信息，是否值得关注 |
| 必要依据 | 采购范围、任务、交付物、项目阶段 | 文章内容、方法、产品变化、案例、研究证据 |
| 不应误判 | 行业名相同就等于能投；公司被提到就等于采购方 | 没有采购预算就无价值；个人作者就不值得看 |
| 评分名称 | 保留现有招标 AI 评分及其业务含义 | 新增“AI 参考价值”，明确与招标分数含义不同 |

行业动态建议沿用五个判断维度的形式：业务关联、信息增量、证据与来源、实际参考价值、时效性或长期价值。新闻看是否有新进展，论文和方法还应看长期参考价值。

本稿不规定评分权重和入选分数线，也不直接套用招标分数线。先由用户标注真实文章“值得看／一般／不相关”和原因，再用 100–200 条覆盖不同类型的样本校准。可先收集少量样例帮助讨论，但不能把少量样例当作已完成校准。

推荐要求：

- 技术研究与同行动态没有预设优先级。默认“最新”遵守真实时间；“推荐”兼顾两类内容，避免大量企业通稿淹没技术资料，也不为凑比例补入低价值文章。
- 标题含“地质”不足以证明相关，应判断是在讲地质软件、业务研究，还是与公司无关的内容。
- 关注企业、软件和主题是线索，不是无条件入选许可证。
- 推荐理由必须能回到来源核验；不把研究推测写成已验证结论。
- 用户可以标记“值得研究”“不相关”“重复”，管理员据此调整规则；一次点击不能自动修改全局规则或重算全部历史。
- AI 没有运行时仅显示规则命中或人工推荐，不冒用 AI 评分。

“不感兴趣”用于处理单篇内容，不替代信源管理：

1. 默认只隐藏当前文章，并记录原因（重复、与业务无关、广告太多、研究太泛、暂不关注等）。
2. 原始资料仍在内部留痕，可撤销、复查和用于规则校准；不因为一篇文章的反馈自动屏蔽整个公众号。
3. 如果用户确认整个公众号都不再需要，文章详情和信源库都提供清晰的“取消关注／停用信源”入口；停用后不再安排新的采集，已有资料仍可搜索、收藏和查看。
4. “不感兴趣”与“删除”分开。被抑制的文章不进入首页、日报和推荐，管理员仍能在反馈记录中恢复或修改状态。

## 6. 信源管理与首批接入方案

### 6.1 一个信源管理区，两类用途

招标信源和公众号信源放在同一个“信源库”是合适的。它们都是内容进入系统的渠道，区别应由“来源类型、费用、采集方式、默认用途”表达，而不是拆成两套互不相通的管理页面。这样用户以后不断增加公众号时，不需要先判断它属于哪个产品栏目，系统按文章内容再分流。

后台继续把信源和业务规则放在相邻区域。建议“信源与业务”下包含：信源库、招标匹配规则、行业关注规则。信源库默认提供“全部／招标信息／行业动态／两者／待验证”筛选；列表中的“用途”是默认倾向，不是对每篇文章的最终裁决。行业关注规则里设置行业、内容类型、企业、产品、技术主题和排除项。

信源列表采用中文表格，工具栏提供新增、编辑、启用、停用、试采集和查看记录。每个信源显示：名称、机构或作者、渠道、用途、行业、免费或付费、采集计划、最后成功时间、新增数量、异常原因。面向用户可将“停用”显示为“取消关注”，并在确认文案中说明“停止未来采集，保留已有资料”。停用是可恢复的；停用信源不删除已有内容和历史记录。

新增信源时，管理员依次完成：

1. 填名称和地址，选择官网／公众号／订阅／论文来源／手动资料等可理解的来源描述。
2. 选择“招标信息”“行业动态”或“两者都可能”；这只是默认用途，最终按每篇内容归类。公众号默认建议选“行业动态”，但不禁止其中出现的正式采购公告进入招标信息。
3. 选择常见行业及关注主题。一个来源可覆盖多个行业。
4. 显示接入是否需要付费服务、是否已配置、可读取标题摘要还是正文。
5. 进行有范围限制的试采集，展示真实样例、预计栏目、重复情况和请求次数，再启用。

需要较复杂适配的站点，由维护人员完成接入，业务用户不填写程序或解析表达式。尚未接通的来源显示“待接入”，不能给出已在持续更新的假象。

### 6.3 微信公众号与论文的特殊要求

- 微信公众号不能承诺输入名字就能稳定、免费取得全部历史文章。需核实账号身份、采集服务可用性、费用和每次可取范围。
- 官网与公众号发布相同内容时，优先使用已验证可用、成本较低的来源，公众号补充独有内容。
- 管理员可以粘贴单篇链接补录。读不到时允许补标题、摘要、作者和日期，记录为“人工补充”，保留原链接；补录不伪装为系统已读全文。
- 论文先收元信息和公开摘要；有可读取正文时才做基于正文的分析。预印本、会议论文、期刊论文、公众号解读分别标识。
- 公众号解读引用论文时，同时保留解读链接和可核验的论文原始入口。
- 默认展示标题、摘要和原文链接。全文展示依来源允许范围配置；内部收藏备注不随公共页面、订阅或 Agent 接口公开。

## 7. 每天两次更新与费用设计

### 7.1 后台采集计划

后台“设置 → 采集与费用”提供全局采集开关、默认更新时间、下一次执行时间、上一次实际执行结果、两栏目的新增数。

默认计划为北京时间 08:00、17:00。这两个时间代表开始采集，完成后更新“最后成功更新”；当天没有新增也应如实显示。后台可以增加一个可选的第三批次，但首期不建议为了行业动态启用第三批次。

- 所有启用信源默认遵循全局两次计划；公众号、补查任务和自动调频不能悄悄增加付费采集批次。行业动态和招标信息先共用这两个批次，只有明确需要时才把某类信源调整为第三批次。
- 批次内按服务限制逐项执行，不要求在整点同时请求所有站点。
- 同一信源同一批次最多安排一次常规列表检查，分页、正文读取和有限重试计入该批次的请求与费用。
- 手动采集是单独操作，明确显示范围，并同样受上限约束；刷新网页不算手动采集。
- 失败不被记作成功。漏跑时在下一个允许批次按最后成功位置有界补漏，不一次性补跑所有错过的时刻。
- 新增信源默认从启用后的新增内容开始；历史回溯单独设置条数或时间范围与预算，不能悄悄全量补历史。
- “不感兴趣”规则应在采集入库后、付费 AI 分析前尽早执行；它可以减少后续处理费，但不能绕过原始资料留痕和误判恢复。

### 7.2 三个控制项不能混为一谈

| 控制项 | 解决的问题 | 面向用户的说明 |
| --- | --- | --- |
| 更新时间 | 什么时候去查新内容 | 每天两次，不是全天不断拉取 |
| 付费请求次数上限 | 最多调用多少次外部服务 | 是次数保护；每天两批不等于每天两次 API 请求 |
| 费用预算 | 最多愿意花多少钱 | 采集与 AI 分项记录，同时受全站总预算约束 |

例如 10 个付费公众号每天查两次，假设每次只调用一次列表接口，就是每天 20 次列表请求、30 天 600 次。正文、分页和 AI 分析可能另计。这只是请求量演示，不是人民币报价。

后台费用页至少分为“付费采集”“AI 分析”，按供应商、栏目和信源查看。显示今日、本月的调用量、估算费用及估算依据。未取得价格时显示“费用未知”，不能显示 0 元；最终账单以服务商为准。

人民币预算保护须以可核验的价格和用量为基础，按预计支出预留额度。价格未知时不能承诺金额封顶，也不自动启用新的付费来源；已启用服务仍须有请求次数上限。界面区分估算与服务商已确认账单。

本稿不假定用户的月预算。付费来源启用前先确定额度；预算不足时暂停相应付费任务。AI 评分、摘要、翻译、归并和报告等费用都要纳入统计，不能只计算采集费。

### 7.3 降低重复支出

- 先识别重复与明显无关资料，再处理新内容；行业研究使用自己的相关性规则。
- 同一内容未变化时不重复 AI 分析；改分类、切页面、重新打开文章不触发收费。
- 付费分析优先覆盖新增相关内容。深度论文分析作为明确的后续操作，不自动对所有论文全文反复分析。
- 招标与行业动态可以设置各自的使用额度，两者合计不能突破全站预算；同一资料的共享成本只记一次。
- 不自动切换到另一家付费模型继续扣费；替代服务需有明确配置和预算。
- 用户对文章的“不感兴趣”反馈不触发重新分析；只有规则范围升级、人工要求复核或新的原文版本出现时，才进入后续处理。
- 信源被停用后不再抓取新内容；已有文章不被删除，也不因停用而改变历史栏目和评分。

## 8. DeepSeek 不可用时的产品行为

以下是拟实现的使用规则，不代表现有版本已完整支持。

| 功能 | AI 不可用时应如何表现 |
| --- | --- |
| 阅读已有内容 | 正常显示已有文章和历史分析结果 |
| 已验证可用的非付费信源 | 按采集计划获取；能否成功仍取决于来源可用性 |
| 第三方付费公众号采集 | 看采集服务自身是否可用、是否有预算，与 DeepSeek 是否充值分别判断 |
| 基础分类 | 使用已有明确来源规则或人工分类，标清依据；无法确认则待分类 |
| 标题与摘要 | 显示原始标题、来源提供的摘要或人工补充内容，不生成假的 AI 摘要 |
| AI 评分与推荐理由 | 保留历史结果；新内容显示“待分析”，不显示 0 分，不标为 AI 精选 |
| 行业动态列表 | 已确认属于该栏目且可展示的内容进入“最新”；AI 精选不足时说明原因，不让所有资料卡在不可见状态 |
| 招标字段 | 只展示已核实值；没有截止日期或预算则标未知，不推算成已确认信息 |
| AI 简报 | 暂停新 AI 简报；可查看原始条目清单和历史报告，不把旧报告标成今日新生成 |
| 恢复后 | 展示待分析数量、建议批次和费用范围，由管理员选择后分批处理；不自动清空全部历史积压 |

若收到明确余额不足反馈，应暂停该服务并提示管理员；其他失败原因按真实信息显示，不能全部归为欠费。普通读者看到“待分析”，后台看到具体服务状态和操作入口。

## 9. 四个典型使用过程

### 场景 A：阅读地质软件研究

用户进入“行业动态 → 地质与矿业”，选择“技术研究”，找到公众号“地质”的新文章。列表能看清标题、原文发布时间、系统收录时间及是否已分析；点击后在系统内阅读本地 Markdown 快照，有价值就收藏，并可通过“隐式建模”主题筛选找回。没有招标预算、没有采购任务不影响收录。

### 场景 B：跟踪同行

用户选择超图、新点、龙软、3DMine 或迪迈，看到与该企业有关的产品、案例、研究及新闻。文章与企业是官方发布、被报道主体还是引用关系，应能分辨；不同媒体重复报道同一事项不会刷屏。

### 场景 C：研究论文

用户搜索“隐式建模”，能查到论文原始条目、相关软件以及公众号解读。能分辨发表年份、系统收录时间、论文状态和读取深度。新近发现的旧论文进入资料检索，不冒充新发表论文；打开后优先在系统内阅读 Markdown 版本。

### 场景 D：未充值继续使用

用户打开行业动态仍可浏览、筛选、收藏；管理员补入链接可保存原始资料。新内容清楚显示待分析。即使 AI 不可用，已保存的 Markdown 文档仍可在系统内完整阅读。费用页能区分采集是否正常、AI 是否暂停，不会因反复打开页面再次收费。

## 11. 验收标准

验收以真实样例和实际运行记录为准，不以“页面能打开”或“接入类型存在”代替业务完成。

| 编号 | 操作或样例 | 应看到的结果 |
| --- | --- | --- |
| A01 | 分别打开招标采购、标前、中标和行业动态 | 四个入口清楚；技术文章不混入招标列表，三个招标阶段不混成一类 |
| A02 | 导入“地质”的一篇已核验技术文章 | 正确落入行业动态，能追溯原文；没有采购任务不被排除 |
| A03 | 导入同行产品发布、项目交付案例、正式中标公告 | 分别归入对应类型；交付或自述中标不被误标为正在招标 |
| A04 | 同一内容由官网和公众号重复发布 | 最新列表不重复刷屏，能看到其他来源；不重复分析未变化正文 |
| A05 | 查看一篇只有日期的文章和一篇日期未知的文章 | 不编造时间；未知日期不会按收录时间伪装为今日发布 |
| A06 | 导入一篇老论文及新发表的解读 | 能区分论文年份和解读发布日期，两者建立关联 |
| A07 | 测试 AI 暂停状态 | 原始内容仍可访问、筛选、收藏；新内容待分析，不虚构分数与摘要 |
| A08 | 测试付费公众号采集不可用 | 信源标明失败或服务未配置，保留已有资料，提供手动补录入口 |
| A09 | 观察连续两天的真实采集记录 | 自动新批次只在 08:00、17:00 开始；补查、自动调频和重试不绕开全局计划与预算 |
| A10 | 反复刷新页面、切筛选、查看已读资料 | 不新增付费采集与模型调用 |
| A11 | 达到请求或费用上限，再尝试普通与手动任务 | 对应付费服务均受约束；后台说明暂停原因和下次可运行条件 |
| A12 | 恢复 AI 服务 | 不自动大批量分析积压内容；管理员可选择范围后有预算地继续 |
| A13 | 切换地质、水利、政务，查看企业与研究内容 | 分类和推荐理由符合样例；两类同等重要，无一类被规则统一排除 |
| A14 | 新增或修改关注规则 | 中文操作，预览样例，保留规则版本及操作记录；不自动改写历史结论 |
| A15 | 访问新增后台菜单及其内部链接 | 均留在后台管理范围，配色、导航和主题切换与现有工作区一致 |
| A16 | 查看采集时间、处理状态与费用 | 显示真实记录；采集成功、AI 完成与有无新增能区分；未知费用不显示为零 |
| A17 | 对一篇公众号文章标记“不感兴趣” | 当前文章被隐藏并记录原因，不删除原始资料，也不自动停用整个公众号 |
| A18 | 在信源库停用一个公众号，再恢复启用 | 停用后不再安排新采集；恢复后从新的增量位置继续，已有资料与操作记录保留 |
| A19 | 在统一信源库中新增公众号，并筛选“行业动态” | 信源与招标信源在同一库管理，公众号文章按内容归入行业动态；正式采购公告可以关联进入招标信息 |
| A20 | 连续两天观察行业动态和招标信息 | 两类内容默认共用 08:00、17:00 两个批次，不以页面浏览或热点变化触发额外采集 |
| A21 | 打开一篇已成功获取正文的公众号文章 | 在系统内进入 Markdown 阅读器，不跳转外部网页；标题、作者、段落、图片、表格、引用和原文发布时间可读 |
| A22 | 打开一篇正文不完整或包含微信互动组件的文章 | 明确显示缺失或未转换部分；不伪造完整正文，原文链接只作为详情底部的追溯入口 |
| A23 | 在阅读器的“更多”菜单下载一篇已保存文章 | 可下载 Markdown 文件及相关本地附件，正文中的图片引用不失效或明确提示缺失；页面不把下载作为主按钮 |
| A24 | 今天首次获取一篇 2024 年论文 | 二级菜单计入“今日获取”，文章同时显示“今日获取”和“历史资料”，原文发布日期仍显示为 2024 年 |
| A25 | 打开“地质与矿业”二级菜单 | 显示今天实际新获取的文档数；数字不把历史总量、未读数、重复抓取或 AI 分析数算进去 |
| A26 | 重复抓取同一篇未变化文章 | 不增加今日获取数量，不产生重复文档或重复 AI 分析；正文快照保留版本记录 |
| A27 | 在文章详情和信源库查看已关注的“地质”信源 | 两处都能看到“已关注”和“取消关注／停用信源”；确认后停止未来采集，但保留已有文章、收藏和历史记录，可再次启用 |
| A28 | 查看不同状态和内容类型的列表、阅读器及后台页面 | 浅蓝、暖象牙、淡紫、淡薄荷绿和淡琥珀色含义一致，文字清晰；颜色只辅助信息层级，不遮挡正文和操作 |

首批信源验收要形成清单：每个候选分别写明“已接通／仅支持手动／待接入”、样例、失败原因和费用依据。没有通过试采集的源不能标为已上线。
