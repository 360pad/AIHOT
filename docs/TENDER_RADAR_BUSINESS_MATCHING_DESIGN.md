# Tender Radar：企业能力、关键词与大模型后端设计

日期：2026-10-11。状态：第一轮实现已落到本分支；数据库、模型调用和真实业务样本验收尚未完成。

本稿对应 Issue #4「企业业务知识规则」与 #5「招投标相关性分析 Prompt」，根据本次交流重新定义业务判断。它补充 `TENDER_RADAR_ARCHITECTURE.md` 的初版配置方案；不是重新建设采集系统，也不是增加 CRM、自动投标或模型训练平台。当前分支已按此设计补充配置、分析后端、测试队列和管理界面。

## 1. 核心决定

**先判断采购方要买什么服务、形成什么成果，再判断公司能做其中哪部分。行业是背景，不是准入条件。**

例如，政府、水利单位、旅游景区、某某矿业公司采购测绘服务，均按同一项测绘能力判断。标题没有“矿山”不影响矿业单位测绘项目的识别；出现“矿山”也不能让普通设备采购自动相关。

后端必须分别回答三个问题，不能混成一个分数：

1. **业务相关性**：实际采购内容是否包含我们关注的交付？依据在哪里？
2. **参与环节**：是独立服务、明确分包/标包，还是综合项目中的业务组成部分？不能由“有相关内容”推断“公司能独立投整个项目”。
3. **当前价值**：适合标前跟进、当前公告跟进、学习中标结果，还是历史复盘？

以下规则不再成立：必须属于五个固定行业之一；必须命中完整关键词；出现“矿山+测量”即通过；没命中关键词即丢弃；预算高可以抵消业务不相关；过期等于业务不相关。

## 2. 企业业务配置：能力为主，场景为辅

### 2.1 初始能力目录

| 能力 | 任务与成果线索 | 配置依据与边界 |
|---|---|---|
| 测绘与空间数据服务 | 工程测量、矿山验收测量、土方测量、无人机测量、航测/摄影测量、水下/水深测量、多波束/单波束、断面测量、地形图、地图编制、空间数据建库与更新 | 用户明确可做；不要求软件、平台或特定行业词 |
| 档案整理与数字化服务 | 档案整理、分类、扫描、著录、编目、数字化加工、数据质检、电子文件归档 | 用户明确可做；人工整理本身就是交付，不必附带系统开发 |
| 软件与业务平台 | 系统开发、整合迁移、迭代升级、系统运维、政务服务、社会治理、建筑监管、电子档案管理系统 | 来自已确认关注的样本；识别实际采购模块，不自动承诺整项目承接能力 |
| 数据治理与 GIS 应用 | 数据治理、公共数据处理、时空数据、GIS 应用、三维地籍、实景三维成果应用 | 来自已确认关注的样本；与测绘、平台能力可同时命中 |
| 监测感知与系统集成 | 视频联网、河湖监管、水文监测、低空巡护、城市生命线、物联监测及集成 | 来自已确认关注的样本；区分监测服务/系统建设和单纯货物采购 |
| AI 场景应用 | 监管识别、智能体、执法助手、政务模型应用等明确应用开发交付 | 来自已确认关注的样本；不因出现“AI”即判相关 |

上述目录是可编辑的业务配置，不是新增六个不可变的源码分类。水利、矿山、政务、建筑、教育、文旅、农业等单独作为 `contexts` 场景信息。一个项目可匹配多项能力、多个场景。

测绘与档案是用户明确的交付能力；其余项首先表示用户确认关注的业务范围。资质、人员、业绩、软硬件供应能力、联合体条件没有提供时，后端必须标“待核验”，不能将关注范围等同于投标资格。

### 2.2 每项能力需要配置的内容

- 稳定编号、中文名称、启停状态。
- **能力描述**：我们提供的服务与成果，供模型理解；不只是词表。
- **关注级别**：重点、常规、观察。由管理员设置，只影响排序和提示，不改变事实判断。
- 任务、方法、成果的词语及常见表达；正例、易混淆反例。
- 已确认的能力边界、尚待确认的相邻业务。

不在一期增加任意脚本、复杂规则语言、知识图谱或独立向量数据库。公司能力目录规模较小时，直接将完整能力说明与精选示例提供给模型。

### 2.3 保留关注，但不冒认能力的样本

用户样本包含尾矿库闭库工程、渠道整治、河道治理、泵站建设、水资源论证、地块图则调整等。不得因为“工程”二字全部拒绝，也不得推断公司能承接全部施工、勘察设计或规划咨询。

处理规则：先读取具体采购范围；有明确测绘、监测、平台、数据或档案任务时匹配对应能力。只有整体工程名称、尚不清楚相关任务时进入“观察/待确认”，保留用户关注标记。用户确认相邻服务确实可做后再扩充能力配置，而不是模型自行扩大公司业务。

## 3. 关键词的职责：找线索，不代替语义判断

### 3.1 词语按语义角色管理

| 角色 | 示例 | 作用 |
|---|---|---|
| 服务动作 | 测量、测绘、整理、扫描、编目、开发、迁移、运维 | 帮助定位采购任务 |
| 方法或技术 | 无人机、航测、多波束、单波束、摄影测量 | 帮助理解任务方法；不自动等于服务采购 |
| 交付成果 | 地形图、断面成果、土方量报告、档案目录、电子档案、业务系统 | 帮助确认公司能力对应的成果 |
| 对象或场景 | 河道、尾矿库、地块、机关文书、工程、矿山 | 补充服务对象，不作为必备行业词 |
| 机构背景 | 某某矿、矿业公司、某某局、某某学校 | 识别采购方；本身不证明购买了什么 |

“工程+测量”“档案+整理”可以作为组合线索，但组合表达式仅用于提示与定位。后端不能在整篇正文分别找到两个词就认定组合成立：必须落在同一项采购任务、同一标包或可证明的语义关系中。也不要求两个词相邻，更不要求固定顺序。

### 3.2 词语通道与语义通道同时存在

- 命中词语：标记命中位置，优先定位相关需求段落，交给模型判断词语角色。
- 未命中词语：仍进入大模型语义预筛；模型可以从任务和成果识别能力。不能只抽样检查无命中内容，再把其余直接丢弃。
- 新的表达：模型可建议同义词或组合线索，管理员确认后加入配置；不得自动发布扩词。
- 来源接口的搜索词只能作为辅助查询。除非已验证完整性，不能以关键词查询取代来源列表的正常覆盖。

预算不足、模型停用或调用失败时，记录“待分析”，不是“无关”。可以排队、复用回执、选择合适的预筛模型，但不得以节省调用为由静默丢掉无关键词记录。

### 3.3 必须通过的语义区分

以下是专门构造的验收例，不是用户提供公告的原文：

| 输入含义 | 预期判断 |
|---|---|
| 某某矿业公司采购年度地形测量、提交地形图 | 相关：测绘；采购方名称不需要命中“矿山” |
| 政府采购工程范围内的高程、断面及土方量测算 | 相关：测绘；“工程”和“测量”不必连续出现 |
| 采集库底高程，形成水下地形图和断面成果 | 相关：测绘；即使没有完整“水下测量”关键词 |
| 无人机设备采购，无数据采集服务或系统交付 | 不能仅凭“无人机”归为测绘；按已配置的设备业务边界判断 |
| 体温测量仪、理化指标测量 | 不属于测绘能力 |
| 施工合同要求承包人自行放线和保管工程档案 | 是履约附带义务，不因此成为独立测绘或档案商机 |
| 采购纸质档案整理，未要求扫描或软件 | 相关：档案整理 |
| 同一采购包同时采购档案柜和档案数字化服务 | 保留数字化服务匹配，不因“档案柜”否定整个项目 |
| 矿业公司采购办公家具 | 不因“矿业”属于关注场景就判相关 |
| 招标代理公告提及某个信息化建设项目 | 区分本次购买的代理服务与目标建设项目；后者至多是间接线索 |

## 4. 后端处理流程

```text
来源发现、去重 → 抓详情与必要附件 → 提取项目/标包/任务及证据
                                      ↓
                         关键词线索 + 大模型能力匹配
                                      ↓
                   相关 / 明确无关 / 证据不足待确认
                                      ↓
                 阶段与时效判断 → 两次机会价值评分
                                      ↓
                  摘要、分类 → 项目归组 → 平台与日报
```

### 4.1 采集与材料准备

复用已存在的采集、正文任务、回执、预算熔断和去重机制。来源层负责拿到真实材料，不承担公司业务词过滤。

材料保留来源 URL、发布时间、正文版本及段落编号；附件需要时记录附件 URL、文件/页码及解析状态。缺正文、附件失败、只有列表摘要，均作为材料质量状态传给业务分析。

长公告先识别采购需求、服务范围、技术要求、成果清单、标包等章节。词语命中只用于优先定位，不能成为唯一切片依据。超过单次模型窗口时分段读采购范围并合并结果；无法读完关键范围要保留覆盖状态。不能把“前几千字没看到”当成整个公告没有相关业务。

### 4.2 项目、标包与任务分解

分析层按“公告 → 项目条目 → 标包 → 采购任务”理解材料。只有原文存在相应结构时才建立层级，不虚构标包、分包或项目编号。

- 一条采购意向可列多个项目；数据库仍可保留一条原文，但分析结果必须保留多个项目条目。
- 每项任务提取“动作、对象、方法、成果、采购角色”，并引用证据。
- 区分采购范围、履约附带义务、单位背景、引用的历史项目。
- 不同任务分别匹配能力，不能把不相关任务的数量平均进去、稀释一个明确相关标包。

### 4.3 大模型相关性判断

优先将现有预筛升级为结构化的“任务提取 + 能力匹配”，不要再无条件增加一个功能重复的模型调用。现有结构化步骤消费该结果并补充展示分类；必要时复核证据不足项。

模型输入：版本化企业能力配置、原始标题与采购内容、材料覆盖情况、词语线索、适量正反例。输入中不带“命中即通过”的指令，也不让来源档位、预算大小决定业务相关性。

模型输出遵守下表；最终状态由后端依据已验证结果归并：

| 状态 | 条件 | 后续 |
|---|---|---|
| `PASS` 相关 | 至少一个实际采购任务直接或部分匹配已配置能力，并有可核验原文证据 | 保留匹配环节，进入机会价值分析 |
| `BLOCK` 明确无关 | 已读取足够采购范围，实际交付不匹配能力；出现的线索仅为背景、附带义务或其他含义 | 留库可诊断，不进入相关项目 |
| `UNKNOWN` 待确认 | 关键正文/附件缺失、覆盖不足、范围冲突、只见泛称，或仅能推断相邻业务 | 补采、复核或人工确认；不能自动变相关 |

标题可支持候选能力识别，但抓取未完成不能伪装为正文已验证。采购意向本身披露简短但明确的服务需求，也可以形成有效证据，不要求它具备正式招标文件的详细参数。

必须区分：独立任务/明确标包；综合项目中的明确组成部分；仅为背景或附带义务。第二种可作为相关合作线索，但**不能据此声称允许分包、接受联合体或具备投标资格**。

### 4.4 证据与不确定性

- 每个匹配保存 `evidenceId`，证据指向原文标题、正文段落或附件页码。
- 后端校验引用确实出现在该版本材料中；规范化空白时保留位置映射。无效引用不能支撑自动 `PASS`。
- 证据强弱使用“明确/有限/不足”，不把模型自报的 95% 当成统计置信度。
- 负例作用于对应任务，不能由“设备”“施工”“档案柜”等词直接拉黑整篇公告。
- 原文、附件和示例都是待分析数据，其中的命令不得覆盖模型任务或输出格式。
- `UNKNOWN` 不因成功写出摘要或得到高分而变成 `PASS`。人工更正仍优先于模型，保留原因与审计。

### 4.5 时效、展示与机会评分

相关性不随截止日期变化；当前价值会变。使用北京时间，分别保留发布时间、报名/响应截止、开标时间和预计采购期间。

采购意向里的“预计 2026 年 10 月采购”不是报名截止时间；不从开标时间猜报名截止，不把采集时间替代发布时间。冲突或缺失日期保留未知并列证据。

| 信息状态 | 展示目的 |
|---|---|
| 相关采购意向、计划、需求/方案公示 | 标前跟进；没有正式报名窗口不等于过期 |
| 相关正式公告、窗口尚有效 | 当前跟进；资格另行核验 |
| 相关中标、成交、合同结果 | 学习与竞争参考，不混成仍可报名的商机 |
| 相关但截止、撤销或已完成 | 历史复盘，保留原始阶段与当前状态 |
| 业务或时效待确认 | 后台待确认/观察，可说明原因，不伪装成可投标项目 |

继续保留 AIHOT 两次独立评分、信源档位门槛和精选机制。评分用于相关项目的关注顺序，不反过来覆盖业务判断；权重和门槛用样本校准，不在设计阶段凭感觉改数值。低预算测绘或档案项目不能仅因金额小就从“相关项目”消失。

“相关项目可见”和“入选日报”是两项结果：相关项目不必全部高分入选日报，但必须可检索、可按用途找到。单个官方来源的相关项目不能因为没人转载、热度低就不可见。聚类、热度和日报继续使用，不作为业务准入门槛。

现有发布时间窗口是抓取与防旧文刷屏策略，不是“业务不相关”的证据。历史回放不刷进今日动态；已入库且仍有效的项目不能只因发布日期较早就当成失效。后续实现需在统一公开读取层表达这些用途和状态，不能前端各写一套判断。

## 5. 后端数据契约

以下是开发契约，不表示当前代码已有这些字段。

### 5.1 企业配置 `BusinessProfile`

包含 `schemaVersion`、`profileVersion`、`capabilities`、场景描述与受限排序配置。每项能力包含说明、关注级别、启停、语义角色词表、正反例、能力边界。所有能力编号按当前配置校验，不在源码中枚举企业的全部能力。

关键词组合只支持受限的词组/语义角色配置，不支持执行任意表达式或脚本。完整的“工程测量”等常用词仍可保留，但不会成为匹配前提。

### 5.2 业务分析 `BusinessMatchResult`

| 字段 | 内容 |
|---|---|
| `schemaVersion / profileVersion / promptVersion / inputRevision` | 结果格式、企业配置、提示词与原文版本 |
| `label / reason` | 相关、无关、待确认及简要依据 |
| `materialCoverage` | 正文/必要附件读取状态，已读范围、缺失项 |
| `projects[]` | 公告内项目条目；保留条目编号或名称及证据 |
| `projects[].tasks[]` | 标包信息、动作、对象、方法、成果、采购角色及证据引用 |
| `tasks[].matches[]` | 能力编号、直接/部分匹配、匹配依据及证据引用 |
| `tasks[].participation` | 独立采购/明确标包、项目组成部分、待核验；不代表资格结论 |
| `contexts / organizations` | 场景；采购单位、代理、中标方等原文实体及角色，不依赖预置公司名白名单 |
| `noticeType / temporalFacts` | 映射现有内容类型；原始日期、精度、证据、冲突 |
| `missingInformation` | 需补采或人工核验的问题 |
| `evidence[]` | 引用文本、材料版本、位置、来源 URL，附件页码如适用 |

`label`、展示用途、当前有效性及 `selected` 由后端规则汇总。模型不直接发布内容，也不自行决定预算熔断、可投标资格或公开权限。

公告至少一个任务明确相关，可汇总为 `PASS`；其他任务的未知信息仍保留。只有不存在已确认匹配、而关键范围不完整或存在相邻业务时汇总为 `UNKNOWN`。`BLOCK` 必须具备足够的采购范围证据。

业务结果先写入现有 `analyses.output` 的独立对象，与原始回执对应，继续使用已有 `relevance` 三态。现有单一 `category` 仅作兼容展示投影，不作为能力识别依据。档案和测绘保留独立能力编号，多能力不会被压成一个行业；现有分类链接不随本次改造改名失效。

公开摘要只含必要业务结论及原文链接；企业能力配置、完整证据和内部判断在管理员后台使用。不因模型读取正文而开放全文展示。

## 6. 可配置、可测试、可追溯

### 6.1 配置的唯一来源

一期建议新增根 `industry/business.json` 作为首次初始化的能力配置，格式由后端 schema 校验；**这是拟实施文件，本次不创建**。不新建 `industry/tender/` 或第二套业务目录。

运行时以已发布企业配置为唯一来源。复用现有 `settings` 存储草稿、不可变版本快照和当前版本指针，管理员修改走专用后端接口及审计，不开放任意设置键修改。初始化只在缺配置时导入，不覆盖后台已保存内容。

发布以事务保存新快照、切换当前指针并记录操作者。回退是切换到旧快照，不覆盖已发布内容。共用提示词只描述分析方法，企业能力和词语由配置注入；不能继续在 Markdown 和后台各维护一份不同的公司词库。

每个分析任务绑定同一份配置快照。模型回执缓存键必须包含材料版本、企业配置内容哈希、提示词/格式版本及模型。否则“后台改了业务配置但重用旧判断”会让测试失真。

新配置影响之后的任务；历史结果不悄悄重写。管理员可选定记录批量重分析。旧版本任务晚完成时不能覆盖已生效的新版本结果；人工更正不能被模型重跑冲掉。测试结果不修改正式分析与发布状态。

### 6.2 前端将使用的后端操作

此处约定业务操作，不在本次实现页面或固定路由名：

| 操作 | 必须具备的行为 |
|---|---|
| 读取配置、保存草稿 | 中文能力、级别、词语与示例；按草稿版本防止并发覆盖 |
| 测试公告或粘贴材料 | 显式指定草稿/已发布版本；异步提交 worker，返回任务编号 |
| 查询测试结果 | 显示词语线索、采购任务、命中能力、原文证据、待确认原因与分步耗时/费用 |
| 发布、查看历史、回退 | 先校验再切换版本，审计可追溯；不自动重算全部历史 |
| 标注结果 | 可标相关/无关/待确认，并细分能力、参与环节及日期错误；保留原模型结果 |
| 重分析指定记录 | 同一正式业务引擎、同一预算与回执机制，结果注明版本 |

测试和生产调用同一业务判断函数，不另做一套“看起来正确”的预览逻辑。打开页面只读结果；付费模型调用只在授权提交的 worker 任务里执行，仍受预算与开关约束。

### 6.3 用户反馈不是自动训练模型权重

“相关但漏了、无关却进了、能力判断错了、日期识别错了”分开记录。反馈保留公告/项目条目、材料版本、原判断、人工标签、原因、操作者和时间；不复用现有通用访客留言字段来混存业务标签。

先用结构化反馈完善能力说明、同义表达、易混淆反例和评测集，管理员测试通过后发布配置。单条反馈只纠正该记录，不自动扩成全局规则。初期不做模型微调，不声称使用几次就自动学会，也不把所有正例全文塞进每次提示词。

## 7. 真实样本验收

### 7.1 样本登记

以用户两份文本附件和本会话逐条提供的公告为验收原始清单。保留原始标题、URL、手工备注及原文获取状态，不先把清单换成更容易跑通的新例子。

规范化 URL 时仅移除跟踪参数，保留 `articleId`、`ggid`、类别等业务参数。样本身份按“来源公告 + 项目条目/标包”登记：同一项目重复粘贴可以合并；同一个链接对应两项不同采购意向，必须分别验收任务覆盖，不能仅按网址去重就少一项。

例如附件中的“水利遥感监测工作底图”和“河湖动态遥感监测影像采购及系统维护”使用同一个江苏公告链接，需要核对是否为同文中的不同项目条目，不能未经核实擅自合并。断裂 URL、手工日期错字和“预计采购月被记为报名时间”等，回看原文确认，不凭清单补造事实。

### 7.3 分开验收两条链路

**采集覆盖**：发现列表 → 详情/必要附件 → 入库 → 可定位项目条目。实时来源窗口和历史回放分别报告。手工导入清单只能测试后面的语义链路，不能冒充列表自动发现成功。

**业务判断**：使用已获取的原始材料 → 正确能力 → 可核验依据 → 正确相关性/用途 → 平台可见。已过期的九月样本仍用于能力回归，不伪造为十月的新公告，不刷进今日商机。

每条输出来源、项目条目、数据库记录、材料状态、配置版本、能力判断、证据、展示位置和失败环节。原文无法获取时明确列阻塞；不能用标题相似、测试通过或信源“健康”替代这一证据。

验收目标：全部用户样本逐项有去向；正文已证实相关的样本不能被关键词、行业、金额或热度门槛漏掉；所有已确认相关项目均能在正确用途下找到。相邻业务未确认、原文不可达等必须单列，不计为通过，也不能从分母中静默删除。

### 7.4 评测与发布门槛

- 扩展现有 SelectBench 的评测契约：分别评价相关性、能力命中、参与环节、证据和时效；保留原有精选评分评测，不把“该看”与“应进日报”混用。
- 反馈样本分开发集和留出集；同一项目的转载、续发和同文标包放在同一分组，避免泄漏。
- 加入本稿的跨行业正例、无关键词正例、同词异义反例、混合采购、正文后部才出现业务、模型失败与预算不足等难例。
- 报告相关项目召回率、查准率、待确认率、关键业务分组表现、证据有效率和单位处理成本。不能只报总体准确率。
- 对本轮已确认的漏判/误判、`UNKNOWN` 自动转 `PASS`、无效证据发布等确定性错误设置回归门槛；未知能力边界先让用户标注。
- 对概率性的质量门槛先建立基线并比较新旧版本。没有真实样本评测前，不宣称达到某个准确率，不凭空设“80 分才相关”。
